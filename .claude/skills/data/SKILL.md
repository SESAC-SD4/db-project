# /data — 샘플 데이터

## 1. 먼저 확인

- `teams/<팀이름>/schema.sql`을 읽는다. `CREATE TABLE`이 없으면 쓰지 않고 `schema.sql`부터 쓰라고 안내한다
- psql에서 `schema.sql`을 에러 없이 실행했는지 묻는다. 아직이면 먼저 실행하게 한다
- 처음이면: 표마다 몇 행쯤 넣을지 팀에게 묻는다. 정하지 않으면 표마다 5~10행
- **기능 추가 중이면**(`data.sql`이 이미 있으면): 새로 만들지 않고 지금 `data.sql`을 바뀐 표에 맞게 고친다. 있던 데이터의 뜻은 그대로 옮긴다(예: 가게의 분류가 연결 표로 옮겨 가면 같은 가게 · 같은 분류의 짝으로). 고친 뒤 **무엇을 어디로 옮겼는지** 표 · 칸 단위로 짧게 말한다(예: "가게의 분류 7개를 연결 표로 옮김 · 새 짝 2개 더함"). 어느 가게 · 어느 행인지는 말하지 않는다. 쿼리 결과가 어떻게 달라질지도 말하지 않는다

## 2. data.sql 쓰기

`teams/<팀이름>/data.sql`을 이 모양으로 쓴다.

```sql
-- 샘플 데이터: \i teams/<팀이름>/data.sql
BEGIN;

INSERT INTO ... VALUES ...;   -- 다른 표가 가리키는 표(부모)부터
INSERT INTO ... VALUES ...;   -- 가리키는 표(자식) · 연결 표는 뒤에

COMMIT;
```

- `BEGIN` … `COMMIT`으로 감싼다. 중간에 하나라도 에러가 나면 전부 들어가지 않는다
- `GENERATED ALWAYS AS IDENTITY` 칸(id)은 넣지 않는다. `schema.sql`이 표를 새로 만들므로 id는 넣은 순서대로 1, 2, 3 … 이 된다. FK 값은 그 번호로 적고, 표마다 `-- 1 홍길동, 2 김철수 …`처럼 번호를 주석으로 남긴다
- 기능 쿼리에서 찾을 거리가 생기게 섞는다
  - 연결이 하나도 없는 행 몇 개 (예: 게시물이 없는 사용자) — LEFT JOIN으로 찾을 거리
  - 여러 개와 이어진 행 몇 개 — GROUP BY로 셀 거리
  - 비어 있어도 되는 칸(NULL 허용)에는 빈 값 몇 개
- `CHECK` · `UNIQUE`를 지키는 값만 넣는다

## 3. 실행 안내

다 쓰면 팀에게 psql에서 실행하게 한다. **응답에서 어느 행이 질문의 답이 될지는 밝히지 않는다**(`/ask`에서 팀이 예상할 거리다). `data.sql` 안의 번호 주석은 그대로 둔다.

```
\i teams/<팀이름>/schema.sql
\i teams/<팀이름>/data.sql
```

- `COMMIT`이 나오면 표마다 `SELECT count(*) FROM 표;`로 행 수를 확인하게 한다
- 에러가 나면 팀에게 **에러 메시지를 소리 내어 읽게** 하고, 어느 줄 무엇 때문인지 함께 찾는다. 에러 뒤의 `COMMIT`은 `ROLLBACK`이 되므로 아무것도 들어가지 않았다는 것도 확인한다
- 고친 뒤에는 **`schema.sql`부터 다시 실행하고** `data.sql`을 실행하게 한다. `ROLLBACK`으로 행은 사라져도 id 번호는 이미 쓴 것으로 남아서, 그대로 다시 넣으면 id가 1이 아닌 번호부터 시작하고 FK 값이 어긋난다
- 에러 원인이 `schema.sql`이면 고칠 곳을 말로만 알려 준다(Claude는 `schema.sql`을 고칠 수 없다)

끝나면 다음 단계를 알려 준다.

- 기본: "이 서비스의 화면이나 버튼 중 DB에서 무엇을 꺼내야 하는 기능 하나를 골라 `/ask <기능>`을 부르세요."
- 기능 추가 중: "`\i teams/<팀이름>/queries.sql`로 이전 쿼리를 전부 다시 돌려 보세요. 에러가 나거나 결과가 달라진 쿼리가 있나요?"
