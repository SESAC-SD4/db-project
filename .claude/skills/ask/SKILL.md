# /ask — 기능을 SQL로

기능: $ARGUMENTS

기능이 비어 있으면 "이 서비스의 화면이나 버튼 중 DB에서 무엇을 꺼내야 하는 것 하나"를 말해 달라고 한다. 예: "가게 목록 화면 — 분류별로, 평균 별점과 함께" · "내 주문 내역". `README.md`의 "기능 쿼리"에 기능 이름을 적는다.

## 1. 기능을 표로 다시 말하기

`teams/<팀이름>/schema.sql`을 읽고, 이 기능이 **어느 표의 어느 칸을 꺼내는지** 한두 줄로 말한다. 팀이 말하지 않은 조건(예: "없는 것도 0으로")을 더하지 않는다 — 필요해 보이면 질문으로 묻는다. **맞는지 묻고, 팀이 답할 때까지 SQL을 쓰지 않는다.**

## 2. SQL

- 먼저 "직접 먼저 써 보시겠어요?"라고 한 번 묻는다
- 팀이 써 오면 → 고치지 말고 그대로 실행해 보게 하고 3번(예상)부터 간다
- 팀이 쓰지 않으면 → Claude가 쓴다. 이번 주 문법(`docs/rules.md`)으로, 한 줄에 절 하나씩. 날짜는 값을 직접 쓴다(`now()` 쓰지 않음). `SELECT` 목록 안의 서브쿼리 · `coalesce`처럼 규칙에 없는 문법은 쓰지 않는다 — 그 때문에 NULL이 나오면 4번에서 화면 기준으로 판정한다(예: "빈칸을 0원으로 읽기로 한다")
- 함정(행이 불어남 · `count(*)` · NULL)을 미리 설명하지 않는다. 결과를 보고 4번에서 찾게 한다

## 3. 실행 전에 예상

SQL을 보여 준 뒤 **실행하기 전에** 팀에게 묻고 답을 기다린다.

> 몇 행이 나올 것 같나요? 꼭 나와야 하는 행 하나를 `data.sql`에서 찾아 보세요.

## 4. 실행과 판정

팀이 psql에서 실행하고 결과를 붙여 넣으면 이것을 함께 본다.

| 볼 것 | 어떻게 |
| --- | --- |
| 행 수 | 예상과 같은가. 다르면 어느 쪽이 맞는가 |
| 한 행 손으로 확인 | 3번에서 찾은 행이 맞게 나왔는가 |
| 빠진 행 | JOIN에서 짝이 없는 행이 빠지지 않았는가 (LEFT JOIN이 필요한 기능인가) |
| LEFT JOIN 뒤 `count(*)` | 짝이 없는 행이 0이 아니라 1로 세어지지 않았는가 |
| 불어난 행 | 연결 표 둘을 한 번에 JOIN해서 같은 행이 여러 번 세어지지 않았는가 |
| NULL | 비어 있는 칸 때문에 빠지거나 잘못 세어진 행이 없는가 |

어느 값이 틀렸는지 Claude가 먼저 말하지 않는다. 3번에서 찾은 행과 결과를 팀이 비교하게 한다.

틀렸으면 팀이 무엇으로 찾았는지 말하게 하고, 고친 SQL로 3번부터 다시 한다. **틀렸던 SQL도 남긴다** — 팀이 쓴 것이든 Claude가 쓴 것이든 발표 거리다.

## 5. queries.sql에 남기기

`teams/<팀이름>/queries.sql` 끝에 이 모양으로 덧붙인다.

```sql
-- 기능 N: <기능>
-- 쓴 사람: <팀 / AI> · 예상: <행 수> · 실제: <행 수>
-- 판정: <맞음 / 틀렸다가 고침 — 무엇으로 찾았는지>
-- 틀렸던 SQL: <있으면 한두 줄로>
SELECT ...;
```

기능 추가 중에 이전 쿼리를 고쳤으면, 그 쿼리 위에 `-- 변경: <기능 이름>에서 <무엇 때문에> 고침` 한 줄을 더한다.

기본 기능 쿼리가 세 개가 되면 `git add teams/<팀이름>` → 커밋 → push하고 Pull Request를 열라고 알려 준다(`README.md` "3. 제출"). 그다음은 `/next`.
