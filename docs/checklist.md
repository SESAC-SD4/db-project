# 설계 기준표

ERD와 `schema.sql`을 이 기준으로 판정합니다. 1~6번은 수업에서 칠판에 쓴 감별 기준표, 7 · 8번은 이 프로젝트에서 더한 것입니다.

| # | 기준 | 수업에서 본 곳 |
| ---: | --- | --- |
| 1 | 칸 하나에 값이 여럿 들어가는 곳이 없는가 (`tag1, tag2`처럼 칸을 늘린 것도 실패) — **제1정규형** | 장르 · 나라 나누기 (`listed_in` → `genres` · `title_genres`) |
| 2 | N:M마다 연결 표가 있는가 | `title_genres` · `title_countries` |
| 3 | FK가 N 쪽에 있는가 | `titles.rating_id` (등급 하나에 작품 여럿) |
| 4 | 연결 표의 PK가 두 FK의 묶음인가 (또는 같은 짝이 두 번 못 들어가게 `UNIQUE`가 있는가) | `PRIMARY KEY (title_id, genre_id)` |
| 5 | PK가 이름이 아니라 번호인가 · id가 `bigint`인가 | `genres.id` + `name UNIQUE` |
| 6 | 요구사항에 **없는** 것을 지어내지 않았는가 | — |
| 7 | FK마다 `ON DELETE`를 정했는가 (가리키는 행이 지워지면 같이 지울지, 막을지) | `ON DELETE CASCADE` |
| 8 | 요구사항 문장마다 그 내용을 담을 표 · 칸이 있는가 | — |

## 4번의 예외: 같은 짝이 다시 생겨야 할 때

먼저 물어봅니다: **"같은 짝이 두 번 들어가는 게 맞나요, 틀린가요?"**

| 경우 | 예 | 설계 |
| --- | --- | --- |
| 두 번이면 틀림 | 같은 게시물에 같은 사람이 좋아요 두 번 | 두 FK 묶음을 PK로 (4번 그대로) |
| 두 번이 맞음 | 같은 회원이 같은 책을 **다시** 빌림 · 같은 손님이 같은 가게에 리뷰를 또 씀 | 그 표에 자기 `id`를 두고, 날짜처럼 그 한 번을 구분하는 칸을 둔다 |

**예외가 아닌 것**: 같은 메뉴를 **다른 주문**에서 또 시키는 것. 주문이 다르면 짝(주문, 메뉴)도 다릅니다. `(1, 5)`와 `(7, 5)`는 다른 짝이라 두 FK 묶음 PK로 둘 다 들어갑니다.
